# 0011 Releases only via trusted publishing

- In each train's repository (0049), only its `.github/workflows/release.yml` publishes, via npm OIDC. Packages require 2FA and disallow tokens. No npm token anywhere.
- Before a release, `.github/workflows/candidate.yml` builds a candidate for staging to try, with the release's gate: it sets the version, builds, packs each package with `npm pack` and uploads the tarballs with `integrity.json` (each tarball's sha512 integrity) as the Actions artifact `<version>-<short sha>`. It publishes and tags nothing.
- Release only releases: it takes a candidate's run id and publishes that run's tarballs, building nothing, so the bytes staging walked are the bytes on npm. It refuses a candidate that is not a passed Candidate run of the released commit, at the version asked, byte for byte as its `integrity.json` records (`scripts/candidate-check.ts`). It dry runs, publishes and tags, with no second test run, using the existing CI result.
- It releases only a commit whose `staging-walk` commit status, set by the walker after walking the candidate on staging, passed (`scripts/staging-walk-gate.ts`). Thomas, the repository owner, can release without it by dispatching the release with `override_reason`; the reason goes into the job log and the GitHub Release's notes. An override from anyone else is refused.
- It runs from main or a branch named `hotfix/<major>.<minor>.x`, only for a commit whose CI push run on that same branch passed: it reads CI's result for that exact commit (`scripts/release-gate.ts`) instead of testing again, and says why in the job log when it refuses.
- One version for a train's packages (0049), published in order, the optional ones last; the workflow tags `v<version>` (`contents: write`). The trierarch's train tags a commit on top of the released one that sets the Aeolus Fleet plugin's manifests to the version, off main's history, so the tag holds the plugin of that version under its version: `aeolus-trierarch upgrade <version>` installs the plugin from it.
- After the tag, the workflow creates the GitHub Release `v<version>`, its notes built by `scripts/release-notes.ts` from the merged pull requests carrying the label `<version>`: titles with links, grouped into features, fixes and other changes. No changelog file: git and the labels are the source.
- The Aeolus Fleet plugin carries the trierarch train's version. The marketplaces install it from main by default, so after a main release the workflow also commits the plugin's version to main; hotfix releases do not update main, which carries newer work. The packages on main keep 0.0.0.
- 0.0.0 is the name placeholder. npm configures a trusted publisher only for a package that exists, so a new package's 0.0.0 is published once by hand by its owner (`npm publish --access public`, no provenance) to claim the name; then its trusted publisher is set to `release.yml` and tokens are disallowed, and from then on only the workflow publishes it.

Why: A leaked token cannot publish; npm and git versions always match; a harness that installs the plugin from a tag gets the plugin of that release under its version, since both harnesses cache the plugin by its manifest's version.

Rejected: `NPM_TOKEN` secret; publishing releases from a laptop; running the tests again in the release (the same gate twice); tagging the released commit itself (its plugin manifests say the version before); a second tag on main's plugin version commit (two tags per release).
