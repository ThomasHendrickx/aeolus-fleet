# 0034 Network rules: who may send to whom

- Core defines the rule format: a network rule says that the ships matching one label selector may send to the ships matching another. A label selector is a set of label value ids (0031); a ship matches when it carries every one of them, an empty selector matches every ship, an unknown id matches none. Rules select by labels only, never by a ship's type. Allow-only: no deny rules, no precedence. A fleet holds at most 200 rules (`NETWORK_RULES_MAX`), and a selector at most 20 value ids (`SHIP_LABELS_MAX`, as a ship carries no more), each once.
- A fleet's network settings are its rules, or none, with a version. A fleet that never set rules has none at version 0. Setting replaces the whole list and moves the version, writing NetworkRulesSet with the version and the number of rules (null for none). An empty list allows only the fixed exceptions; none is all-to-all, today's default.
- Setting takes the scope `fleet:network` (`fleet.setNetworkRules`, also on REST and MCP as a fleet action), given at commission as any fleet scope (0002); argo holds it. Nothing else changes the rules.
- With rules set, every send is checked at send time, in its unit of work, against the sender's and the recipient's labels as they are then: a send no rule allows is refused (`NOT_REACHABLE`, FORBIDDEN, one fixed message, no reasons), nothing of it is stored, and its idempotency key stays unused. A stored message is delivered whatever changes later.
- A send to a type keeps with its delivery the ships of the type the sender may reach at send time; only they may claim it, and a ship that takes the type later may not. None reachable refuses the send. With no rules, or from argo, any ship of the type may claim it.
- An operator's resend is a new message, checked at its own send time as the original sender sending: refused, it is recorded and the original stays undeliverable, for Dismiss.
- Two fixed exceptions, never subject to rules: argo sends to every ship and every ship sends to argo; and a ship answers a message it received (a delivery to it, or one of its type it claimed) when the answer names it (inReplyTo) and goes to that message's sender.
- Every refusal is recorded in the transaction that refuses, which commits only the record: the sender, the recipient (a ship, or a type with each ship of it), the label values each carried then (ids and texts, so a later change keeps the record true), the settings version and when. Its own table (`reach_refusals`, ids `rfs_`), not the event log, so no timeline or `fleet:read` shows it; only argo reads it (`fleet.reachRefusals`, the latest 100, newest first).
- A send and a change of rules take turns on a per-fleet advisory lock on the settings: shared for a send, exclusive for a set. So every send is checked against exactly one version, the one its refusal names, and a stream of sends never starves a change (Postgres queues a shared request behind a waiting exclusive one, which a row lock does not).

Why: a message is a prompt, so reach is the operator's way to group ships, contain a rogue or breached ship and protect sensitive ones (design on #260). Rules on labels only their owner assigns, never the ship itself (0031), so relabelling cannot widen a ship's own reach. The sender learns nothing about the rules, so a refusal cannot be used to map them; the record lets argo look deeper. 0016 holds: the rules are the operator's, Aeolus adds none.

Rejected: deny rules and precedence (mixed defaults confuse, as in Kubernetes NetworkPolicy); rules on type (#412); checking again at claim (a stored message is the fleet's promise); refusals in the event log (any `fleet:read` ship would read them); reasons in the refusal (they map the rules); a row lock on the settings (a stream of sends starves a change).
