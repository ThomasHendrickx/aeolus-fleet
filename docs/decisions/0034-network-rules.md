# 0034 Network rules: who may send to, read or manage whom

- Scope says what a ship may do; a rule says where (0046). Each rule names one verb (`send`, `read` or `manage`) and says that the ships matching one selector may do it to the ships matching another. Force and discovery ride send, resend rides read (0046, 0047). Every type of interaction has a where: a verb, or identity, ownership or assignment.
- A selector is a list of terms that must all hold, and an empty selector matches every ship. A term is a label (0031) or the owner (0045), plus one of:
  - an exact value (a label value id, or an owner's ship id);
  - `*`, any value;
  - `#`, a value the ship on the other side carries too, on the same label or the owner on both sides. A `#` on one side only is refused.
  A selector matches an actor: a ship by its labels and owner, an account by the `group` values in its account token (0052, 0058). An unknown id matches none. Allow-only: no deny rules, no precedence, never by type. Limits in 0037.
- **Built-in rules**, core's own, seeded at fleet create, shown first in the rule list, marked built-in:
  - argo to and from every ship, every verb, except that a ship reads argo only by a rule, so argo's messages are not every ship's. Never off: a bad rule set must not lock argo out.
  - the owner's ship to the ships it owns, every verb. Never off: a human is always responsible (0045).
  - an answer to the sender of the message it answers (inReplyTo, a delivery to it or one of its type it claimed), send. Never off: an allowed send must be able to get its answer.
  - a connected plugin reads every ship. Activating a plugin in a fleet gives that permission: argo's Connect in the console connects the plugin's ship (`fleet.connectPlugin`, `fleet:connect` (0053), `PluginConnected`), and a release or a retire of the ship ends it (`PluginDisconnected`). The fleet's registered networking plugin (0035) reads as a connected one does. Never off, so saving rules never narrows what a plugin reads.
  - the viewer reads every ship. An actor holding `fleet:network` may turn it off.
  - the installation manages person ships and the ships they own. Never off: a leaver is always released (0055).
  - open: every ship to every ship, one per verb. The networking plugin removes it, by its own action.
  Turning a built-in off or on is its own action with an event, never a side effect of setting other rules.
- The rules beside the built-ins are the networking plugin's (0035) and the declared ones (0037), set whole with a version, `NetworkRulesSet`.
- **Send:** every send is checked at send time, in its unit of work, against both ships' labels and owners as they are then. A refused send (`NOT_REACHABLE`, FORBIDDEN, one fixed message, no reasons) stores nothing, and its idempotency key stays unused. A stored message is delivered whatever changes later. A send to a type keeps the reachable ships of the type as its only claimants; none reachable refuses it. A resend is checked as the original sender sending.
- **Read:** every `fleet:read` read is filtered by read rules. A message is readable through its sender or its recipient. A ship outside read reach shows name, type and status only. Fleet-wide views count only what the caller reads; `follow` and `events` carry only that. A connected plugin (squadrons, the trierarch plugin, the networking plugin) reads fleet-wide by its built-in rule, and a ship holding `fleet:on-behalf` (0046) may read on behalf of a named ship by naming it in the `Aeolus-On-Behalf-Of` header of a `fleet:read` read, getting exactly that ship's read reach (never argo's or the viewer's), so the plugin serves a person only what the person may read and never holds the person's crew token.
- **Manage:** every `fleet:manage` call, every grant on a live ship and every change of owner is checked against manage rules on the target ship (0053).
- Every refusal is recorded in the transaction that refuses, which commits only the record: sender, recipient, both ships' labels and owners then, the ship that read on behalf of the sender if one did, the verb, the settings version and when. It goes in its own table (`reach_refusals`, `rfs_`), read with `fleet:explain` (`fleet.reachRefusals`, the latest 100).
- An actor holding `fleet:explain` asks which ships a ship reaches now, per verb (`fleet.explainReach`). Each answer names the exact rule that allows it: a built-in, a networking plugin rule, or a declared rule and its declarer. It records nothing, and there is no dry run. The sender's refusal and discovery (0047) name no rule.
- A check and a change of rules take turns on a per-fleet advisory lock on the settings, shared for a check and exclusive for a change, so every check uses exactly one version.

Why: "the what (scope) vs where (network) is an all type of interactions": reach groups ships, contains a rogue or breached one and protects sensitive ones, for reading as much as sending (`fleet:read` read every payload before). "Hidden behaviour is a source of debugging nightmare": every way a ship can reach another is a rule argo can see, and every change an event. A sender learns nothing of the rules, so a refusal cannot map them; argo needs the rule to debug.

Rejected: `#` linking two different labels; deny rules and precedence (mixed defaults confuse, as in Kubernetes NetworkPolicy); rules on type (#412); checking again at claim; refusals in the event log; reasons for the sender or in discovery (they map the rules); hidden fixed exceptions; a verb per interaction (three cover every crossing); an owner label (a second source of truth); a row lock on the settings (a stream of checks starves a change).
