# 0020 Installation

One server hosts many fleets for a hosting service (the account app). Above fleet sits the installation. Its procedures (`installation.fleets.create`, `list`, `get`, `delete`) live on the one tRPC router, guarded by an installation token from the server's environment; without a token they do not exist. Create and delete take the caller's request id and answer a replay with the first answer. The fleets the installation creates may share an operator email, the creating admin's for each fleet it creates; the email of argo's own sign-in (a password) is no other operator's, so a create under it is refused and the hosting service still tells a fleet made before by its email. A hosted fleet has no argo's own sign-in: an account signs in as argo through a one-time sign-in ticket the installation issues for it, naming the account (2 minutes, single use, stored hashed), which the console redeems for a session as a password sign-in does, and a hosted console serves no password form (0054). Two procedures concern accounts: ending console sign-ins by an account (0055), and cutting off an account's tokens (0058). The installation is also an actor in each fleet (0057): holding the fixed scopes and built-in manage reach defined in 0057, it acts through the same fleet calls as any actor; the account app acts as it. The installation keeps limits as configuration: default ship, daily message and schedules per ship limits and a default minimum schedule interval for fleets (0062), a default retention (0066), and a cap on fleets, each fleet following a default or setting its own; unset is no limit, Aeolus sets none of its own (0016 holds), and each limit refuses exactly at its boundary. Deleting a fleet removes every record with its `fleet_id`, its events included (the one exception to append-only events), and writes no event; the server logs it. A short transaction marks the fleet deleted (`fleets.deleted_at`), so it reads as gone at once (no find, list or count, its secrets, operator account, console sessions, sign-in tickets and crew requests end, and its data keys are shredded, their rows kept until the batches as what they sealed restricts their delete); the removal pass in the 30 second maintenance pass then removes the rest in batches of 500 children first, the history, then the schedules, leases, ships and every other record, and the fleet row last, each batch under the fleet's removal lock and its own transaction, and takes up again, on the next pass or after a restart, any fleet marked deleted that a failure left unfinished. `installation_requests` is the one table that belongs to the installation: a create's row goes with its fleet, a delete's row keeps only the request's hash, so nothing of a deleted fleet stays.

Why: hosted Aeolus needs fleets made and removed by a service, and a deleted fleet must be gone.

Rejected: the whole delete in one transaction (a big fleet cannot finish in 30 s); a second API door for the installation; soft delete or partial backup; an event for the delete (the fleet's log goes with it); keeping the deleted fleet's id or email to answer a replay.
