# 0068 Sealed fleets: payloads under the company's own key

- **What it keeps out.** A fleet may turn sealing on; a sealed fleet stores no payload readable, so a copy of the database, another tenant and, once the company cuts its grant, the host and the maintainer read none. The ends, their model providers (0063) and the gateway for the ships it crews (0054, 0056) read what reaches them. One mechanism per fleet, the same hosted and self-hosted.
- **Payloads only.** Every payload in a sealed fleet is sealed, whoever wrote it: a ship's, a schedule's, a resend's, a meeting contribution, and core's own (pings, meeting notices). Metadata, report notes and details, statements, meeting titles, commission notes and verified facts stay readable; the docs say so, so a crew keeps client data out of them. A question's uuid is metadata: core stores it in its own column at send, so withdrawals and replacements are found on a sealed fleet.
- **Keys.** The company key lives in the company's own KMS, AWS KMS first; core never sees it and asks the KMS to make, wrap, unwrap and rewrap through the `KeyVault` port, every call carrying the encryption context `aeolus:fleet = <fleet id>`. The installation has one KMS principal from its configuration; the company grants it use of its key with a condition naming its fleet id, and no company credential is stored in Aeolus. A data key (`dky_`) is a 256-bit AES key kept only wrapped, by the company key and by the optional recovery key (an `age` X25519 recipient whose public half alone core holds), with a check value; one current per fleet, old ones kept to unseal old payloads.
- **Sealing.** AES-256-GCM, a random 96-bit nonce, additional data naming `aeolus/v1`, the fleet and the row, so a sealed payload moved to another row or fleet does not open. The row keeps the plain payload's UTF-8 byte count, so the 64 KB limit, `message_days` and pruning count the same bytes in every fleet. Core seals on the way in and unseals on the way out; ships, the gateway, plugins and the console send and receive plain text as today.
- **Turning on** (`fleet.turnOnSealing`) checks the KMS makes and unwraps a data key for this fleet and refuses one under another fleet's context (else `KEY_NOT_BOUND_TO_FLEET`), then marks the fleet sealed with its first data key and `FleetSealingTurnedOn` in one transaction. Payloads stored plain before are sealed in batches by the 30 second pass (`FleetPayloadsSealed` when none is left). `fleet.sealing` (`fleet:read`) reads the state, references, availability and key ages, never a key.
- **Both promises hold.** No KMS call runs inside a transaction. A send that cannot get its data key is refused `KEY_UNAVAILABLE` and stores nothing. A receive unwraps before it commits its claim; a key it cannot get rolls the claim back, claiming nothing and counting no attempt, and the delivery waits pending. A read that claims nothing answers `KEY_UNAVAILABLE`, or in a list marks that payload unreadable. An idempotent repeat's hash leaves out the payload; core unseals the stored one to compare.
- **The kill switch.** A server holds an unwrapped data key in memory at most 5 minutes from its unwrap, never on disk or in a log, so a disabled key or a removed grant stops every seal and unseal within 5 minutes; restoring it restores everything, nothing waiting lost. `FleetKeyUnavailable` and `FleetKeyAvailable` mark each change, not each call. With the key cut off, everything that reads no payload goes on; a due schedule's send is refused and recorded, resend is refused, the sealing pass and rotation wait.
- **Rotation.** A new data key at 30 days old (`FleetDataKeyCreated`); the company rotates its key's material in its KMS with no change in Aeolus; changing the company key (`fleet.changeCompanyKey`) rewraps every data key in the KMS, the old key reachable (`FleetCompanyKeyChanged`); changing the recovery key (`fleet.changeRecoveryKey`) wraps every data key to the new one (`FleetRecoveryKeyChanged`), and sets one on a fleet sealed without; a recovery key once set is only replaced, never removed. No payload is sealed again. No person or ship holds a key, so a leaver or a retired ship needs no rotation.
- **Recovery is the company's own.** With a recovery key, core's CLI on the company's computer (`aeolus-core fleet:recover-keys --identity <age identity file> --company-key <new key ARN>`) reads the recovery set (`fleet.recoverySet`), opens each data key locally and wraps it under a new company key in the company's KMS, and uploads them (`fleet.recoverKeys`); core checks the new key as at turning on, an upload naming every data key once, and every check value, one mismatch refusing all (`RECOVERY_KEYS_MISMATCH`), then swaps the wraps in one transaction (`FleetKeysRecovered`). A fleet sealed without a recovery key is refused `NO_RECOVERY_KEY`. The command reaches the fleet over its API with the credentials it already takes (`AEOLUS_URL` and `AEOLUS_CREW_TOKEN`, optionally `AEOLUS_ACCOUNT_TOKEN`, or `AEOLUS_INSTALLATION_TOKEN` with `AEOLUS_FLEET`), and the company's KMS with the AWS credentials on that computer, never sent to Aeolus. No plain data key reaches Aeolus outside the KMS. Without one, recovery is the KMS's own. A key destroyed with no recovery leaves the fleet's sealed payloads unreadable for good: its deliveries wait pending, metadata and events stay, retention prunes only what is finished.
- **Who acts.** Turning on, changing keys and recovery take the scope `fleet:keys` (0046), which the fleet manager holds (0051) and a group may give.
- **The console** renders a sealed fleet's payload as today, marked sealed, with "sealed, key not reachable" in its place when cut off, and never decrypts in the browser (0033). In a sealed fleet a ship's page names the gateway as a reader when the gateway crews it or it is a proxy ship.
- **Proven by tests** on Postgres and a LocalStack KMS in Testcontainers: the refusals change nothing, a restart loses no sealed message, rotation and recovery under races and rollback, a moved payload does not open, no payload or key in a log line.

Why: regulated buyers ask whether the vendor's staff can read their data and whether they can cut the vendor off (Thomas: the threat first is the hosting operator and the maintainer). A key per fleet in the company's own KMS answers both with no client change: the company sees each unwrap in its KMS log and revokes at will, and both promises stand because a refusal stores or claims nothing. A 5 minute cache keeps the KMS's latency and charge off each message for a decision a company takes once. A destroyed key may come back within the KMS's waiting period, so its deliveries wait rather than end. Changing a key is a company decision with its own blast radius, not ship management. Rendering in the console keeps argo, the fail-safe, able to read where the running service reads anyway. The full rules (B1 to B20), flows and scenarios are in [the design](../design/e2e-encryption/e2e-encryption.md).

Rejected for now: level C, ends holding the keys so the running service reads nothing (#1363); other key vaults (#1364); turning sealing off (#1365); an event per payload read (#1366); a company running its own gateway (#1367). Rejected: removing a recovery key once set (replacing it covers a lost or leaked offline key); encryption at rest under a key the host holds alone (the host still reads); end to end between ships (ships and people inside one company are kept apart by scopes, network rules and read reach, not by encryption); sealing metadata or report notes; Aeolus holding a usable copy of a key; a KMS call per send and receive, or a 1 minute cache; making a destroyed key's deliveries undeliverable; `fleet:manage` for keys; never rendering a sealed payload in the console; decrypting in the browser.
