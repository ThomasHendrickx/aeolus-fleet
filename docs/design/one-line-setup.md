# Short setup for a self-hosted fleet

Design for [#1654](https://github.com/ThomasHendrickx/aeolus-fleet/issues/1654), milestone core 0.40.0. Docs only, nothing built. It goes purpose first (section 1), then the lessons to check against (section 2), then the screen it changes (section 3), then the questions still open (section 4). Detailed decisions, the flow and the before and after mockups follow once Thomas agrees the purpose and answers the questions.

## 1. Purpose (to agree)

**The problem.** Someone who wants their own fleet today has to read [Self-host](../guide/self-host.md) and either follow its manual install (install two npm packages, set three settings, `migrate`, `fleet:init`, start two processes) or follow the [aeolus-fleet-selfhost](https://github.com/ThomasHendrickx/aeolus-fleet-selfhost) README (copy `.env.example`, fill up to fourteen settings and five database passwords by hand, pick Compose profiles). Neither signs them in at the end: the Compose README does not say how to run `fleet:init`, and the manual install leaves them to copy a link from a terminal. The site's Run it yourself card can only show those eight lines.

**For whom.** A developer who wants to try Aeolus on their own computer or a server they run, has git, Node and Docker, and has not read the guides yet. Second, the person who later keeps that fleet running with [Run the server](../guide/run-the-server.md): the folder the setup leaves behind is the Compose repository itself, the one supported way to run, upgrade and back up.

**The outcome.** Three lines, run in a terminal:

```sh
git clone https://github.com/ThomasHendrickx/aeolus-fleet-selfhost.git && cd aeolus-fleet-selfhost
npm run init
npm start
```

- `npm run init` writes `.env` from `.env.example`: generated database passwords (and `GATEWAY_SECRET` when the gateway is chosen), the connection URLs and the plugin addresses that match the parts chosen, and the Compose profiles to run.
- `npm start` runs `docker compose up`, waits for core's `/health`, runs `fleet:init` on the first start, and opens the sign-in link it prints, so the person lands in the console on localhost signed in as argo. Its last lines say what is left: connect each chosen plugin under Settings, and answer agents in the console's operator inbox.

Both are scripts in **ThomasHendrickx/aeolus-fleet-selfhost**, beside `compose.yaml` and `.env.example`. No new npm package, no wizard to publish: the clone is the folder, and an upgrade is `git pull`, then `npm start`.

**Out of scope.** TLS and a public address (the self-hoster's proxy, as Self-host says), a person's sign-in on a self-hosted fleet (the [self-hosted sign-in](self-hosted-sign-in.md) design), preparing and joining a computer (Join a machine and the trierarch's setup guide), and anything only the hosted fleet runs.

## 2. Lessons to check against

| | Lesson | Source |
| --- | --- | --- |
| L1 | **Thomas chose the smaller shape.** `git clone`, then `npm run init` and `npm start` inside the Compose repository, no new npm package, three lines on the site's card. This replaces the site design's `npm create aeolus-fleet@latest` and `npx aeolus start`; the parts stay as approved there: core and console always, the gateway, squadrons and the trierarch plugin each optional, and until the gateway has its own sign-in, self-host answers in the console's inbox. | Thomas's answer on PR 1829, option 2; aeolus-site [#98](https://github.com/ThomasHendrickx/aeolus-site/pull/98), `docs/design/site-start/README.md` Q2 and Q3 |
| L2 | **There is one supported way to run every part: the Compose repository.** It builds one image per part from the pinned npm packages, runs core and the console always and each plugin in its own profile, starts plugins only once core's `/health` answers, restarts on failure, binds `127.0.0.1` only, and has a `postgres` profile that makes one owner role and database per part. The scripts drive it; they do not run anything around it. | [self-hosting-operations](self-hosting-operations.md) section 3; [Run the server](../guide/run-the-server.md) section 1 |
| L3 | **Core's repository does not name the other trains.** The scripts know every train, so they live in the Compose repository, on top of the dependency graph. | Decision [0049](../decisions/0049-release-trains.md); self-hosting-operations section 3 |
| L4 | **`fleet:init` runs once and asks nothing; its link works once, for 15 minutes.** A second run refuses, today with exit code 1 like any other failure; `aeolus-core sign-in` prints a fresh link and ends any other sign-in as argo. One self-hosted server runs one fleet. | [Self-host](../guide/self-host.md) sections 3 and 6; `packages/core/src/adapters/cli/fleet-init.ts`; decision [0012](../decisions/0012-operator-is-a-ship.md) |
| L5 | **A plugin works only once argo connects it** from the console's Settings, where the console commissions its ship and hands the secret over server to server. Starting the container is not enough. | Self-host section 7 |
| L6 | **A self-hosted gateway does nothing for a person yet.** It starts, migrates and connects, but nobody signs in to Bridge, a chat or Slack without the account sign-in, and the self-hosted sign-in service is designed, not built. | [Self-host the gateway](https://github.com/ThomasHendrickx/aeolus-fleet-gateway/blob/main/docs/guide/self-host-the-gateway.md); [self-hosted-sign-in](self-hosted-sign-in.md); [Self-hosted variants](../guide/self-hosted-variants.md#answer-your-agents-and-bridge) |
| L7 | **Every setting is read at start; secrets stay out of sight.** `GATEWAY_SECRET` is permanent and in no database; each database password and the settings are backed up beside the databases. Init writes them only into `.env`, where the backup steps already look, and never prints them. A regenerated password or secret breaks a fleet that already has data. | Run the server section 5; self-hosting-operations section 5 |
| L8 | **Versions are pinned, upgrades go in order, migrations only go forward.** `.env.example` holds one pin per train, updated after each release; `.env` must follow it on upgrade. | Run the server section 4 |
| L9 | **Minimal before 1.0**: no compatibility layers, no polish for zero customers. | Decision [0013](../decisions/0013-breaking-changes-before-1-0.md) |
| L10 | **"Trierarch" names two parts.** The trierarch plugin runs on the server; the trierarch runs on each computer, installed by Join a machine's setup line, after the computer is prepared. Decision 0050: a trierarch runs on a computer. | Self-host sections 7 and 8; decision [0050](../decisions/0050-domain-language.md) |
