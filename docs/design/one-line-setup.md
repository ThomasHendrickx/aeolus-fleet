# One-line setup for a self-hosted fleet

Design for [#1654](https://github.com/ThomasHendrickx/aeolus-fleet/issues/1654), milestone core 0.40.0. Docs only, nothing built. It goes purpose first (section 1), then the lessons to check against (section 2), then the questions (section 3). Detailed decisions, the flow, and the before and after mockups of the wizard's terminal and the console it opens follow once Thomas agrees the purpose.

## 1. Purpose (to agree)

**The problem.** Someone who wants their own fleet today has to read [Self-host](../guide/self-host.md) and either follow its manual install (install two npm packages, set three settings, `migrate`, `fleet:init`, start two processes) or follow the [aeolus-fleet-selfhost](https://github.com/ThomasHendrickx/aeolus-fleet-selfhost) README (copy `.env.example`, fill up to fourteen settings and five database passwords by hand, pick Compose profiles). Neither sets up the gateway, squadrons or the trierarch plugin for them, and neither signs them in at the end: the Compose README does not say how to run `fleet:init`, and the manual install leaves them to copy a link from a terminal. The site's Run it yourself card can only show those eight lines.

**For whom.** A developer who wants to try Aeolus on their own computer or a server they run, has Node, and has not read the guides yet. Second, the person who later keeps that fleet running with [Run the server](../guide/run-the-server.md): what the setup leaves behind must be the same supported way to run, upgrade and back up, not a second one.

**The outcome.** One command, `npm create aeolus-fleet@latest`, asks a few questions (the fleet's name, its Postgres, and whether to add the gateway, squadrons and the trierarch plugin, each optional) and leaves a folder holding a configured fleet. In that folder, one command starts it and opens the console on localhost, signed in as argo. The wizard says where that person answers their agents: the console's operator inbox, since Bridge needs a sign-in a self-hosted fleet does not have yet.

**Out of scope.** TLS and a public address (the self-hoster's proxy, as Self-host says), a person's sign-in on a self-hosted fleet (the [self-hosted sign-in](self-hosted-sign-in.md) design), preparing and joining a computer (Join a machine and the trierarch's setup guide), and anything only the hosted fleet runs.

## 2. Lessons to check against

| | Lesson | Source |
| --- | --- | --- |
| L1 | **Thomas picked the commands and the parts.** `npm create aeolus-fleet@latest`, then `npx aeolus start`; core and console always, the gateway, squadrons and the trierarch each optional; until the gateway has its own sign-in, self-host answers in the console's inbox. The site's `after/home.html?wizard` mockup is its acceptance criterion: fleet name and Postgres, then the optional parts, then start opens localhost:3000 signed in. | aeolus-site [#98](https://github.com/ThomasHendrickx/aeolus-site/pull/98), `docs/design/site-start/README.md` Q2 and Q3 |
| L2 | **There is one supported way to run every part: the Compose repository.** It builds one image per part from the pinned npm packages, runs core and the console always and each plugin in its own profile, starts plugins only once core's `/health` answers, restarts on failure, runs one squadrons and one trierarch plugin process, binds `127.0.0.1` only, and has a `postgres` profile that makes one owner role and database per part. A second way to run the parts would need its own answers to all of that. The site's mockup was drawn before this repository existed. | [self-hosting-operations](self-hosting-operations.md) section 3; [Run the server](../guide/run-the-server.md) section 1 |
| L3 | **Core's repository does not name the other trains.** The Compose repository sits on top of the dependency graph so that no train repository names another. A setup that installs the gateway, squadrons and the trierarch plugin knows every train. The site design assumed "a new package in aeolus-fleet". | Decision [0049](../decisions/0049-release-trains.md); self-hosting-operations section 3, rejected options |
| L4 | **The npm name `aeolus` is not ours.** `aeolus` on npm is another maintainer's package with a bin named `aeolus`. `npx aeolus start` inside a folder whose dependencies give a bin `aeolus` runs that local bin; anywhere else it downloads and runs the stranger's package. `create-aeolus-fleet` and `aeolus-fleet` are free today. | npm registry, checked 2026-11-15 |
| L5 | **`fleet:init` runs once and asks nothing; its link works once, for 15 minutes.** A second run refuses; `aeolus-core sign-in` prints a fresh link and ends any other sign-in as argo. One self-hosted server runs one fleet. | [Self-host](../guide/self-host.md) sections 3 and 6; decision [0012](../decisions/0012-operator-is-a-ship.md) |
| L6 | **A plugin works only once argo connects it** from the console's Settings, where the console commissions its ship and hands the secret over server to server. Starting the process is not enough. | Self-host section 7 |
| L7 | **A self-hosted gateway does nothing for a person yet.** It starts, migrates and connects, but nobody signs in to Bridge, a chat or Slack without the account sign-in, and the self-hosted sign-in service is designed, not built. | [Self-host the gateway](https://github.com/ThomasHendrickx/aeolus-fleet-gateway/blob/main/docs/guide/self-host-the-gateway.md); [self-hosted-sign-in](self-hosted-sign-in.md); [Self-hosted variants](../guide/self-hosted-variants.md#answer-your-agents-and-bridge) |
| L8 | **Every setting is read at start; secrets stay out of sight.** `GATEWAY_SECRET` is permanent and in no database; each database password and the settings are backed up beside the databases. A wizard that makes them writes them where the backup steps already look. | Run the server section 5; self-hosting-operations section 5 |
| L9 | **Versions are pinned, upgrades go in order, migrations only go forward.** The Compose repository's `.env.example` holds one pin per train, updated after each release. | Run the server section 4 |
| L10 | **Minimal before 1.0**: no compatibility layers, no polish for zero customers; a second published artefact per train was rejected. | Decision [0013](../decisions/0013-breaking-changes-before-1-0.md); self-hosting-operations section 3 |
| L11 | **"Trierarch" names two parts.** The trierarch plugin runs on the server; the trierarch runs on each computer, installed by Join a machine's setup line, after the computer is prepared (its own user, harnesses signed in, a GitHub sign-in). Decision 0050: a trierarch runs on a computer. | Self-host sections 7 and 8; decision [0050](../decisions/0050-domain-language.md) |

## 3. Questions

Each with options and a pick. Q1 settles the purpose; the others shape the build.

| | Question | Options | Pick and why |
| --- | --- | --- | --- |
| Q1 | Is the purpose in section 1 right, for whom it is and what is out of scope? | 1. As written: a developer trying it on their computer or a server, ending signed in on localhost; TLS, people's sign-in and joining a computer out. 2. Also the public address: the wizard asks for it and writes `PUBLIC_URL`, `CONSOLE_ORIGIN` and `TRUST_PROXY`, the proxy still the self-hoster's. 3. Other | 1: the one line is for the first run; a public address is a few settings in `.env` that Self-host section 5 already explains, and asking for it before anything runs adds a question most first runs cannot answer |
| Q2 | What runs the parts the wizard sets up? | 1. The Compose repository: the wizard writes its `.env` and the profiles, and start runs `docker compose` with them. Needs Docker beside Node. 2. Plain Node processes that start itself supervises, as the site's mockup implies. No Docker. 3. Ask the person, both supported | 1: it is the one supported way (L2), with start order, restarts, one process per plugin and the Postgres roles already solved and tested; 2 builds a second process manager the Run the server guide would have to describe too; 3 is both |
| Q3 | Where do the wizard and the start command live? | 1. In aeolus-fleet-selfhost, published to npm from there with trusted publishing. 2. A new package in aeolus-fleet, core's train, as the site design assumed. 3. A repository of its own | 1: it already knows every train at a pinned version and nothing depends on it (L3); 2 makes core's repository name the other trains; 3 splits what the pins and the Compose file must agree on |
| Q4 | `npx aeolus start` would run another maintainer's package outside the folder (L4). Which start command? | 1. `npx aeolus-fleet start`, a name that is free, from a package the folder depends on; outside the folder it says no fleet is here. 2. `npx aeolus start` as approved, the folder's dependency giving the bin `aeolus`; outside the folder it runs the stranger's package. 3. `npm start` in the folder | 1: same shape as the approved line and never runs someone else's code; it changes one line of the site's mockup, so Thomas decides. 3 is safe but leaves the plugins' other commands (sign-in, stop) without a home |
| Q5 | Is the folder a copy of the Compose files, or does it depend on them? | 1. The folder holds `.env` and a `package.json` that depends on the published self-host package at one pinned version, which carries `compose.yaml`, the Dockerfile and the train pins; an upgrade is one version bump, then start. 2. The wizard copies `compose.yaml`, the Dockerfile and `.env.example` into the folder; an upgrade is copying them again by hand | 1: the pins stay the self-host repository's, as L9 has them, and upgrading needs no merging; 2 leaves every folder drifting from the supported files |
| Q6 | Postgres: what does the wizard ask? | 1. Run Postgres in the folder (the `postgres` profile, passwords generated) or give an existing server's connection URLs, run in the folder the default. 2. Always the `postgres` profile. 3. Always an existing server | 1: the default needs nothing but Docker, and a managed Postgres stays possible as the Compose README allows; the generated passwords go only into `.env` (L8) |
| Q7 | "The trierarch" in Thomas's note: which part does the wizard offer? | 1. The trierarch plugin, as a profile; joining a computer stays Join a machine in the console, which the wizard's last lines point to. 2. The trierarch plugin, and after start it also joins this computer. 3. Other | 1: joining needs a prepared computer (L11) the wizard cannot check, and the server may not be the computer that runs agents |
| Q8 | The gateway does nothing for a person yet (L7). Does the wizard still offer it now? | 1. Offer it, saying plainly that Bridge and chats wait for the self-hosted sign-in and that answers go to the console's inbox until then. 2. Leave it out until the self-hosted sign-in is built, then add it. 3. Offer it without saying more | 1: Thomas asked for it optional (L1), and its settings and secret are in place when the sign-in lands; saying so is what the issue asks |
| Q9 | Plugins need connecting from Settings after start (L6). Who connects them? | 1. The person: start opens the console signed in, and the wizard's last lines say to connect each chosen plugin under Settings. 2. Start connects them itself, which needs a new way to connect a plugin without the console | 1: it needs no new core behaviour; 2 is a second connect path in core for a few clicks, before 1.0 (L10) |
| Q10 | Signing in on later starts (L5). What does start do once the fleet exists? | 1. The first start runs `fleet:init` and opens its link; later starts open the console's sign-in page, and say `aeolus-core sign-in` prints a fresh link. 2. Every start prints a fresh link with `sign-in`, ending any other sign-in as argo | 1: a later start is often a restart on a server, where ending argo's sign-in in another browser by surprise does harm |
