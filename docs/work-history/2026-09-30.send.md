## Goal

A ship sends a message, and gets OK only once the message and its deliveries are durably stored.

## Build

- `send(selector, payload, contentType, idempotencyKey, inReplyTo?)`, requires `messages:send`. The sender is the calling ship: a crew token, or the console session as `argo`.
- Selector `ship`: by id or by name, resolved to the id at send time; `argo` is addressable; a retired or unknown ship is rejected. Selector `type`: rejected unless at least one non-retired ship has that type; one delivery for the type queue.
- Payload at most 64 KB, measured on the serialized payload in bytes; larger is rejected before anything is stored.
- `inReplyTo`: the id of a message in the same fleet; anything else is rejected.
- Idempotency: unique on sender plus key; a repeat returns the original message id and stores nothing new.
- Message, deliveries, event and `NOTIFY` in one transaction; OK only after commit.
- `resend-of` exists in the schema but nothing sets it yet (Needs attention comes after the acceptance test).
- No console page: sending from the console comes with the console work.

Small follow-up decided by Thomas (own commits): no error response ever carries a stack trace, whatever `NODE_ENV` is; errors are still logged on the server. Prove it with a test.

After the first review round, Thomas asked for a quick Sonnet reviewer pass ("the goal is that a merge happens from a rather clean PR"), then answered the open questions:

> 1. Content types: accept any well-formed media type (type/subtype, optional parameters), store it and pass it on untouched. Aeolus is content-blind and adds no policy (ADR 0016).
> 2. Keep the 1 to 256 character idempotency key, the shared ship lock during send, and the notification listener adapter.
> 3. Server failures: the response carries a generic "internal error" message plus a request id; the full error goes to the server log with that same request id. Domain errors keep their specific codes and messages.
> 4. A NUL character (U+0000) in the payload, key or content type is refused as a bad request with a clear message, never a 500.
> 5. Idempotency: same sender, same key, same request (selector, payload, content type, inReplyTo) returns the original message. Same key with a different request is refused with its own error code. Store a hash of the request with the message to compare.
>

## Key decisions

Decided by Thomas (his answers above):

- **Content type**: any well-formed media type (RFC 9110: type/subtype with optional parameters), stored and passed on untouched, case and parameters included; no list of allowed types (ADR 0016). `INVALID_CONTENT_TYPE` (`BAD_REQUEST`) otherwise.
- **Kept**: the idempotency key of 1 to 256 characters, the shared ship lock during a send, the listener adapter.
- **Server failures**: the answer is `Internal error` with the request's id (`data.requestId`); the server log holds the whole error, path, reason and stack, under the same id (`reqId`, the label Fastify's own request lines use). Refusals keep their own codes and messages.
- **U+0000**: in the payload (`INVALID_PAYLOAD`), the idempotency key (`INVALID_IDEMPOTENCY_KEY`) or the content type (`INVALID_CONTENT_TYPE`), refused as `BAD_REQUEST` with "... cannot hold the character U+0000 (NUL)", at the door and in the value objects.
- **Idempotency**: the same sender, key and request (selector, payload, content type, `inReplyTo`) returns the original message; the same key with another request is refused, `IDEMPOTENCY_KEY_REUSED` (`CONFLICT`). The message stores a SHA-256 of the request.

Not dictated by the docs or by Thomas, for review:

- **Selector shape**: `{ kind: 'ship', shipId }`, `{ kind: 'ship', name }` or `{ kind: 'type', type }`; names and types must be handles at the door.
- **Content type bound**: at most 256 characters, parameters included, so a content type stays as small as the ticket it labels.
- **Payload size**: the payload is text; serialized, it is its UTF-8 bytes, which is what Postgres `octet_length` counts. At most 65,536 bytes, checked by the common schema at the door and by the `Payload` value object, both answered `BAD_REQUEST`.
- **The request hash**: SHA-256, through a `RequestHasher` port served by the same adapter as secrets, of one canonical text: the selector as sent (one ship by id and by name are two requests), the payload, the content type exactly as sent, the message it replies to. The order of the selector's fields does not change it.
- **Idempotency key**: opaque. A repeat is checked before the selector, so a retry still gets its OK after the recipient was retired. Keys belong to the ship, so a new session crewing it shares them. Two sends with one key serialise on a transaction-level advisory lock on the sender and the key; the unique index is the backup.
- **Refusals**: `UNRESOLVABLE_SELECTOR` (`NOT_FOUND`) for an unknown ship id, another fleet's ship, a retired ship, an unknown name and a type without an active ship, each with its own message; `IN_REPLY_TO_NOT_FOUND` (`NOT_FOUND`); `PAYLOAD_TOO_LARGE` (`BAD_REQUEST`).
- **Request ids**: a random UUID per request, so an id finds one log line across restarts; never taken from the request.
- **A send holds the ship it addresses `FOR SHARE`** until it commits. A later retire, locking the ship to change it, then waits for the send and sees its delivery, or the send waits for the retire and is refused. Without it, a send racing a retire could get OK for a delivery nobody can ever receive. A type selector takes no lock: a retire never abandons type deliveries.
- **`MessageAccepted`**: actor the sender; ship the recipient ship (none for a type); message and delivery set; details `{ selector, recipientType }`. One event per message: v1 has one delivery per message.
- **Notice**: `pg_notify('aeolus_delivery_pending', '{ fleetId, deliveryId, recipient }')` in the send's transaction. The listener is an adapter of its own on a dedicated pg connection; the integration test needs it (lint keeps `pg` out of tests), and slice 5's long-poll receive will use it.
- **Output**: `{ messageId }`.
- **Stack traces**: tRPC with `isDev: false`, whatever `NODE_ENV` says.

## Noticed, not done

- Retire (after the acceptance test) must lock the ship to change it (`FOR NO KEY UPDATE`, as a new starting prompt does) before it abandons direct deliveries, so the send's `FOR SHARE` serialises the two.
- A type delivery accepted while the last active ship of its type is being retired waits until a ship of that type exists again; nothing tells the sender.
- The listener has no reconnect and no error handler: slice 5 wires it into receive and owns that.
- Notes and location descriptions can still hold U+0000 and then fail as a server failure (now `Internal error` with a request id); Thomas's rule covers the payload, key and content type of a send.
- The whole failure in the log can echo request data when an error message quotes it (a Prisma validation error does), which sits uneasily with "payloads never logged"; nothing in the send path is known to do that now.
- `payloadBytes` counts with `TextEncoder`, which agrees with what pg stores for well-formed text; a lone UTF-16 surrogate becomes U+FFFD (three bytes) in both, so the count still matches, but the stored text is not the text sent.
