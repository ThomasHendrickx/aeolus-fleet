## Goal

A session claims an agent ship with its secret and becomes its crew.

## Build

- `register(shipId, secret, location)`: location is DEVICE, CLOUD, SERVER, or OTHER with a required description. Stored on the lease, never interpreted.
- Refused: unknown or invalidated secret, retired ship, `argo`, a ship whose lease is already held. Unknown and invalidated secrets give one shared error.
- Lock order: lock the credential row first, then open the lease; never lock the ship `FOR UPDATE` (slice 2 work history), so a claim and a new starting prompt serialise correctly.
- On success: the ship becomes Crewed, the credential is marked claimed, and `register` returns a crew token `aeolus_ct_v1_<random>`, stored only as a hash with the lease (decision 0015).
- Every later ship call authenticates with the crew token in a header; the secret works only for `register`. Add one authenticated ship procedure to prove it (`whoami`: ship name, type, fleet).
- Events: ship claimed, with location.
- The fleet list shows the location of crewed ships and "claimed" for their prompt.
- Security: reject state-changing console calls whose Origin is not the allowed console origin (cross-site request forgery from sibling hosts under one domain).

## Key decisions

Not dictated by the docs:

- **Use case name.** `claimShip` in Registry (the blueprint's claim, `ShipClaimed`); the procedure is `ship.register`, the contract's name.
- **Lock order.** The claim locks the valid secret by its hash, reads the ship without a lock, then locks the open lease. A prompt locks the ship `FOR NO KEY UPDATE`, then the secret, so the two serialise on the secret: whoever holds it first wins, the other is refused. A test proves that a claim locking the ship would deadlock.
- **Refusals.** An unknown secret, an invalidated one, another ship's and an unknown ship id: `WRONG_SHIP_ID_OR_SECRET`, 401, "Wrong ship id or secret". A crewed or retired ship: `SHIP_NOT_AWAITING_CREW`, 409, as for the starting prompt, the message says which. argo: `OPERATOR_SHIP_HAS_NO_SECRET`, 403. A location that breaks the rule: 400. The secret lookup no longer filters retired ships, so the domain decides.
- **The secret authenticates nothing but `register`.** The bearer is the crew token; fleet procedures take a crew token or the console session (ADR 0015; the architecture's router table said "ship secret").
- **Crew token.** `aeolus_ct_v1_` plus 256 random bits, SHA-256 in `leases.crew_token_hash`, unique across fleets; a console lease has none. Returned once as `{ crewToken }`. The lookup needs an open lease and a ship that is not retired.
- **`ShipClaimed`** for an agent: the ship itself is the actor; details `leaseId`, `location`, `locationDescription`, as for argo.
- **`ship.whoami`** needs no scope: any caller learns only about itself. It returns ship id, fleet id, name and type; argo gets its own.
- **`register` rate limit**: 10 attempts per client address per minute, its own bucket, as for sign-in.
- **Origin check.** Sign-in, sign-out and every mutation authenticated by the session cookie need `Origin` equal to the console origin; a missing Origin is refused (a browser always sends one with a POST). Checked before the session is used, so a forged call does not renew it. Queries and calls with a crew token are not checked. `CONSOLE_ORIGIN` now defaults to `PUBLIC_URL`'s origin (web and server behind one host, as in the architecture's deployment); CORS headers are always set for the console origin, which the browser ignores on its own origin. Local development sets `CONSOLE_ORIGIN=http://localhost:3000` in `.env`.
- **Location in the list**: `{ kind, description } | null`, null while no session crews the ship; the console words it `<Kind> · <description>` as the design conventions say.
- **Refactor rule**: exactly one `refactor(...)` commit directly after a green commit (a production commit right after a `(red)` one).

## Open questions

1. ADR 0002 still says "Secret lookup returns ship, fleet, kind and scopes in one query". Since ADR 0015 the crew token lookup does that, and the secret is only locked for `register`. Update 0002?
2. Can a claimed secret claim again once its lease ends by `deregister` (slice 6)? This slice refuses only while a lease is held; release invalidates the secret, so only deregister leaves a claimed, valid secret.
3. A `register` whose answer is lost in transit leaves the ship crewed by a token nobody holds; only Release frees it (ADR 0010). Fine for v1?
4. The blueprint's Identity invariant ("An invalid secret fails on the very next call") and `CredentialRevoked` ("All calls with the old secret fail immediately") still read as if the secret authenticates calls; since ADR 0015 it only registers. Reword them to "the next `register`"?
5. A query with the session cookie from another origin still renews the session (it is not a state change in the fleet, and CORS keeps the answer from that page). Leave it, or refuse cross-origin use of the cookie altogether?
