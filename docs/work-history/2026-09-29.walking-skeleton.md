## Questions asked and answered

Asked before writing the schema; Thomas answered:

- **Prefixes for the four tables without one:** `lse_` (lease), `crd_` (credential), `opr_` (operator), `ses_` (operator session).
- **Schema depth:** only the columns and key constraints the architecture states plainly. Ambiguous columns wait for the slice that owns them.
- **Id body:** a lowercase ULID (26 Crockford base32 characters: 48-bit millisecond time, 80 random bits).

Recorded in ADR 0005 (amendment), `docs/architecture.md` and `CLAUDE.md`.

## Key decisions

Technical choices the docs left open:

- **Workspace sources in development.** Each package exports a custom `@aeolus-fleet/source` condition pointing at its TypeScript source. TypeScript, Vitest and `tsx` use it; published packages resolve to `dist`. The server's build turns the condition off so it compiles against common's build.
- **Versions.** TypeScript 6.0 rather than 7.0 (typescript-eslint supports below 6.1). Prisma 7.10, the latest stable (npm's `latest` tag points at an 8.0 release candidate).
- **Partial unique indexes** use Prisma's `partialIndexes` preview feature, so `migrate diff` sees no drift. The payload limit, the one-recipient rule and the append-only trigger on `events` are hand-written SQL at the end of the migration; Prisma does not model them.
- **Foreign keys carry fleet_id**, so a row can never point at another fleet's ship, message or operator.
- **No database default for timestamps**: the Clock port sets every one, so tests control time.
- **Events are append-only in the database**: a trigger rejects UPDATE, DELETE and TRUNCATE.
- **Fastify lives in `src/adapters/http/`** (not in the architecture tree) because it hosts tRPC, and later REST and MCP. `src/app.ts` does the wiring so integration tests run the real composition; `src/main.ts` only starts it.
- **`system.ping` is a use case in `core/shared`** with a FleetCounter port. Counting fleets is the only read not scoped to a fleet.
- **Server defaults:** listens on 127.0.0.1:4000; `DATABASE_URL` is required.
- **Web calls `/trpc` on its own origin**, the same shape as production behind a proxy. `next.config.ts` forwards it to `AEOLUS_SERVER_URL` otherwise; the value is fixed when the app is built.
- **Integration tests run on Postgres 16**, the oldest version the architecture supports, with one container and one database per test file.
- **ESLint config stays JavaScript**: ESLint 10 needs jiti or an unstable flag for a TypeScript config.
- **Release:** accepts only `MAJOR.MINOR.PATCH` (npm needs a dist-tag for a prerelease), and dry-runs all three packages before publishing any, so a problem cannot leave a partial release. The CI dry run uses `0.0.0-ci.<run id>` with `--tag dry-run`, because 0.0.0 is already on npm.

## Open questions

Not answered by the docs, and not needed for slice 0:

1. **The operator as a recipient** (slice 4, operator inbox). Ships can reach the operator ("questions and approvals addressed to the operator"), but v1 selectors are only `ship` and `type`, and a delivery holds a recipient ship or a recipient type. How does a ship address the operator, and what does that delivery hold?
2. **The message sender** (slice 4). A sender is a ship or the operator. One column holding a prefixed participant id, or one column per kind? This decides the unique rule on sender plus idempotency key.
3. **A delivery's resolution** (Needs attention). What does it record: resent, dismissed, abandoned by the operator? A value, a time, or both?
4. **What an event records** (first slice that writes events). Beyond type and time: which ship, message or delivery it concerns, who caused it, a data payload? Timelines per ship and per message thread must be queryable. Related: the architecture has no thread or reply-to on messages. Is threading part of v1?
5. **Lease location** (slice 3). Free text, or a kind (device, cloud, server)? Required on `register`?
6. **Lookups before the fleet is known** (slices 1 and 3). A bearer secret and an operator email do not carry a fleet, so resolving them reads across fleets. Is a global lookup by secret hash and by email the intended exception to "every query is scoped by fleet_id"?
7. **Operator session token** (slice 1). Is the `ses_` id the cookie value, or does a session store a separate random token as a hash? How long does a session live?
8. **`system.ping` once auth exists** (slice 1). It is public now and reveals the fleet count. Does it stay public?
9. **Release extras.** The workflow cannot commit the version back or tag the repository (`contents: read`). Should a release create a git tag or GitHub release? Should prereleases with a dist-tag be possible?

## Noticed, not done

- Migrations at startup under an advisory lock (architecture, "Migrations") are not built; `npm run db:migrate` exists. The published server ships its migrations, but the Prisma CLI is a dev dependency.
- The rule that one context never imports another's internals has no lint rule yet; only the core boundary is enforced.
- Fastify's request log includes the URL, and a tRPC query carries its input in the query string. When a query takes sensitive input, the log serializer must drop it ("never logs secrets or payloads").
- Live updates are to resume from the last event id, but ids generated in the application are not in commit order under concurrent transactions, so a resuming client could miss an event. Needs a design before the live-updates work.
- The published web package bakes the `/trpc` forward target in at build time. How an installer runs the web package is a deployment question.
- `npm audit` reports four high findings, all inside the Prisma CLI's own dependencies (deepmerge-ts, mysql2). Dev only: installers of the server do not get the CLI. The fix is a Prisma downgrade.
- Foreign key columns have no indexes of their own yet; each slice adds the indexes its queries need.
- Branch protection on main (build plan, Thomas's list) can now require the CI checks.
- The architecture's Playwright smoke test belongs to the console work.
