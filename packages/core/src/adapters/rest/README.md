# REST adapter

`/api/v1`: the ship procedures, and the fleet actions a ship with fleet scopes may call, as REST, for ships that are not TypeScript or not MCP-capable. It holds no logic of its own (ADR 0004); lint keeps the core out of it.

- One route per procedure, each a call through the router by `trpc/ship-contract.ts`: `/api/v1/ship/<call>` for every procedure under `ship` (`trpc/ship.ts`), then `/api/v1/fleet/<call>` for each fleet action in `FLEET_ACTIONS`, each needing the scope its procedure checks. A query without input is GET (such as `ship/whoami`, `ship/discover`, `fleet/labels`); every other call is POST with a JSON body, `fleet/list` included, which takes the labels to select ships by. `openapi.json` lists them all.
- The wake stream (decision 0072): `GET /api/v1/ship/wakeups`, the subscription `ship.wakeups` read through the router by `WAKE_STREAM` in `trpc/ship-contract.ts` and written as server-sent events; a refusal before its first event answers as a call's. It stays out of the request duration histogram; `telemetry/wake-streams.ts` counts it.
- `GET /api/v1/fleet/events`: the fleet's committed events (`fleet.events`, `fleet:read`) as server-sent events, read through the router by `FLEET_EVENTS_STREAM` in `trpc/ship-contract.ts`. Each item has the event's number as its `id` and the stream item as `data`; a client opening again sends the last id as `Last-Event-ID`, the console's `lastEventId`. A refusal on opening answers as any call's; once the caller no longer holds, `event: end` carries the refusal's code and message and the stream closes. A comment every 25 s keeps a quiet stream open. It stays out of the request duration histogram too.
- The crew token travels as `Authorization: Bearer`; `register` takes the ship secret in its body. The console session cookie is never read here.
- `GET /api/v1/openapi.json`: the OpenAPI 3.1 spec, generated from the same procedures, with their descriptions and the router's Zod parsers as JSON Schema. Its description opens with the ship protocol (`trpc/ship-protocol.ts`), the text the MCP server sends as its instructions, then what is REST's own.
- `GET /api/v1/docs`: that spec as a readable page titled like the spec, rendered by `@scalar/fastify-api-reference`. The page talks only to the fleet's own server: the server serves the viewer's script itself, the viewer uses the browser's fonts instead of Scalar's font CDN, Scalar's agent, developer tools and telemetry are off, and "Try it" calls the fleet without a proxy.
- A refusal answers with its code's HTTP status and `{ "code", "message" }`; a call without a valid crew token is told to call with the crew token alone, since a ship has no console to sign in to, and one whose lease has ended answers 401 with the code `LEASE_ENDED`. A refusal about a delivery keeps its HTTP status and answers with the delivery's own code, such as `DELIVERY_NOT_IN_FLIGHT` or `DELIVERY_HELD_BY_ANOTHER_SHIP`, so a ship can tell what became of that delivery (#832).
- A failure, in a procedure or in the adapter itself, answers 500 with `Internal error` and the request's id (`requestId`), and the log holds the whole failure under that id. Fastify's own refusals, such as a body that is not JSON, keep Fastify's format for now.
